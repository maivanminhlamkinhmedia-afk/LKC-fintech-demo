# CMS-002 — Creator/Admin Publishing RBAC

Status: SPEC READY  
Depends on: CMS-001 — Financial Publishing Domain Schema  
Target branch: `feature/cms-002-creator-admin-publishing-rbac`

---

## 1. Goal

Establish the server-side authorization foundation for the LKC Fintech CMS publishing system.

CMS-002 defines which authenticated application roles may access the CMS and which publishing operations they are allowed to perform.

The implementation MUST reuse the existing:

- NextAuth authentication
- `User.role`
- `src/lib/roles.ts`
- `src/lib/authz.ts`
- server-side authorization pattern

Do not introduce a second authentication or RBAC system.

---

- SUPER_ADMIN
- ADMIN
- MANAGER
- SALES_MANAGER
- SALES
- CREATOR
- ANALYST
- EMPLOYEE
- CLIENT

CMS-002 does not add, remove, or rename database roles.

No Prisma migration is expected.

---

## 3. CMS Roles in Scope

Only these roles receive CMS back-office publishing capabilities in CMS-002:

### SUPER_ADMIN

Full CMS publishing authorization.

May operate on any article and may perform administrative/editorial publishing actions.

### ADMIN

Full CMS publishing authorization.

May operate on any article and may perform editorial/publishing actions.

### CREATOR

Author role.

May:

- access the CMS authoring area
- create articles
- read own articles
- edit own articles when allowed by CMS workflow policy
- submit own articles for editorial review

May NOT:

- edit another creator's article
- approve an article
- publish an article
- perform administrative CMS operations
- bypass ownership restrictions

### All other roles

MANAGER, SALES_MANAGER, SALES, ANALYST, EMPLOYEE and CLIENT receive no CMS back-office publishing authorization in this task.

Existing non-CMS permissions for those roles must remain unchanged.

---

## 4. Security Principles

Authorization MUST be enforced server-side.

Hiding a navigation link or button is not sufficient authorization.

All future CMS pages, server actions and route handlers must be able to use the authorization helpers created by CMS-002.

Authorization must use the authenticated session user from NextAuth.

Never trust:

- role submitted from the browser
- authorId submitted from the browser
- editorId submitted from the browser
- ownership information supplied by FormData
- hidden form inputs as authorization evidence

User identity must come from the authenticated server session.

## 7. Ownership Policy

CMS-002 must introduce reusable CMS authorization helpers.

Preferred location:

`src/features/cms/access.ts`

The helpers must support authorization based on both:

- role
- article ownership

At minimum provide policy behavior equivalent to:

```text
canAccessCms(user)

canCreateArticle(user)

canReadArticle(user, article)

canUpdateArticle(user, article)

canSubmitArticle(user, article)

canReviewArticle(user, article)

canApproveArticle(user, article)

canPublishArticle(user, article)
```

Exact function names may vary slightly if a cleaner implementation is justified, but the policy behavior must remain equivalent.

User shape should require only the minimum necessary information, for example:

```ts
type CMSUser = {
  id: string
  role: AppRole
}
```

Article policy input should also use only necessary fields.

Do not make authorization helpers depend on browser state.

---

## 8. Ownership Rules

For SUPER_ADMIN and ADMIN:

```text
read any article        ALLOW
update any article      ALLOW
submit article          ALLOW
review article          ALLOW
approve article         ALLOW
publish article         ALLOW
```

For CREATOR:

```text
create article          ALLOW

read own article        ALLOW
read another article    DENY

update own article      ALLOW subject to workflow restrictions
update another article  DENY

submit own article      ALLOW
submit another article  DENY

review article          DENY
approve article         DENY
publish article         DENY
```

All other roles:

```text
CMS back-office access  DENY
```

---

## 9. Workflow Boundary

CMS-002 establishes authorization policy.

It must NOT implement the complete editorial workflow.

Detailed state-transition enforcement belongs primarily to:

- CMS-011 Editorial review workflow
- CMS-012 Fact-check / request changes
- CMS-015 Publish / schedule / unpublish

However, Creator editing must already follow a conservative rule.

A CREATOR may update their own article only when status is:

```text
DRAFT
CHANGES_REQUESTED
```

A CREATOR must NOT directly update their article while status is:

```text
SUBMITTED
EDITORIAL_REVIEW
FACT_CHECK
APPROVED
SCHEDULED
PUBLISHED
CORRECTED
ARCHIVED
```

ADMIN and SUPER_ADMIN ownership authorization is unrestricted by this CMS-002 ownership layer.

Later workflow tasks may impose additional state-transition rules even on admins.

---

## 10. Submit Policy

CREATOR may submit only their own article.

CMS-002 does not need to implement the actual submit server action unless such an action already exists.

The access helper must nevertheless make the authorization rule reusable by CMS-005/CMS-011.

No client-provided `authorId` may be used to establish submit authority.

---

## 11. Publish Policy

Only:

```text
SUPER_ADMIN
ADMIN
```

may receive publication authorization.

CREATOR may never receive:

```text
cms:article:publish
```

CMS-002 only establishes the authorization primitive.

Actual publishing/scheduling behavior belongs to CMS-015.

---

## 12. Review / Approval Policy

Only:

```text
SUPER_ADMIN
ADMIN
```

may receive:

```text
cms:article:review
cms:article:approve
```

CREATOR may not approve their own article.

Even if a Creator is the article author, ownership must never imply review, approve or publish authority.

## 13. CMS Access Guard

Add a reusable server-side CMS guard.

Preferred approach:

reuse:

`requirePermission(...)`

from:

`src/lib/authz.ts`

with:

```text
cms:access
```

Do not duplicate session-loading logic if the existing authorization helper can be reused.

Future CMS pages should be able to use a pattern such as:

```ts
await requirePermission('cms:access')
```

CMS-002 does not need to build the Creator dashboard UI.

Dashboard implementation belongs to CMS-004.

---

## 14. Article Query Scope

Provide a reusable policy/query-scope mechanism so future CMS lists cannot accidentally expose other creators' drafts.

Expected behavior:

### SUPER_ADMIN / ADMIN

Article query scope:

```text
all articles
```

### CREATOR

Article query scope:

```text
authorId = current authenticated user id
```

### Other roles

No CMS article scope should grant access.

A helper such as:

```ts
articleCmsScope(user)
```

may return a Prisma `ArticleWhereInput`.

Exact implementation may vary.

Do not use an insecure empty `{}` scope for unauthorized users.

---

## 15. No Hard Delete Permission

CMS-002 must not introduce a CMS article hard-delete permission.

The CMS architecture preserves editorial history.

No helper such as:

```text
cms:article:delete
```

should be added in this task.

Future archival/unpublish behavior will be handled separately.
